## Intent and constraints

The user wants to tell Rhythm Secretary in chat which captured goal to run against a current reference, see finite usage and time limits, and start the existing server-managed selected-reference Coding Workflow without a setup form.

Scope is one primary coordinator root, one captured goal, the selected_reference_summary_v1 purpose, a current indexed memory-vault reference, the fixed workflow-orchestrator route, and the existing two server-checked criteria. The human should see proposal, pending decision, started/held state, and eventual checked status in chat. They need not type opaque IDs or versions; Secretary can discover candidates and the server must resolve the current identity/version. The desktop Transcript currently has a read-only pending-approval banner while the actionable ApprovalCard is in Shell's notification menu. Add a small actionable bounded-workflow card in the same desktop chat, reusing the existing signed decideApproval/nativeHumanApprovalMaterial path; no setup form or generic approval rewrite.

Out of scope: other managed-work purposes, arbitrary target/profile/model/workspace/tool selection, schedules, additional grants, bypass or auto-approve changes, a new form, provider-semantic claims, production deployment, merge, or changes to the ordinary rhythm_start_coordinator_goal behavior. That tool starts one ordinary async child; it is not finite prepareWorkflowPlan.

Hard constraints: no source-symbol edit before GitNexus impact; no commit before detect_changes. Use a feature branch and draft PR; human merges. The behavioral gate must enter through the new MCP chat tool on actual API plus built fork in tools/dev/sandbox.sh with approved read-only fixtures. Never hand-start API or copy normal app data. Implementers leave the separate integration checkout untouched; root owns the reviewed fast-forward into that checkout. Local agent execution and approvals are SQLite; any added shared column requires Postgres bootstrap assessment. Keep the existing manager/callback membership, provider usage, exact retry, and checked stop.

The design tension is conversational ease versus an explicit, attributable finite usage grant. The smallest end-to-end proof is a signed foreground proposal, one exact signed human approval card, and a signed approval-resume start through the existing finite plan path. Model prose cannot set acknowledgement flags or authorize a budget.

## Proposed flow

1. A read-only signed foreground status/reference query exposes a bounded list of eligible indexed references with human labels and current versions. The server derives actor, project, root, profile, source ID/version, and eligibility. If nothing is unique/current, chat shows a shortlist or hold. The model supplies no path, bytes, hash receipt, or source grant.
2. A dedicated signed foreground proposal tool accepts an existing captured goal selector, eligible reference selector, and Secretary's task-specific estimate for total soft tokens, per-worker wall time, and grant expiry. The server checks current C2/root/project/profile, plan and non-bypass mode, goal state, source/version, and all numeric bounds; it fixes the two-ordinal selected-reference purpose. It creates one dedicated coordinator.workflow.start approval row **even for clean sessions**. A bypass root is ineligible under the existing workflow authority. The card has a server-authored human preview: goal, selected source/version, estimated limits with a short rationale, soft total-token scope (input, output, reasoning, cache, reconciled overrun), manager/descendant/review coverage, and no promise of verified completion. If the human asks in chat to adjust a limit, the server creates a revised proposal and exact approval card; it never mutates a pending card in place. Only the latest proposal for that root/goal may start; an older card cannot fund the revised terms even if approved later. Human decision uses the existing capability plus signature; profile auto-approve cannot decide it. Pending proposal creates no finite authority or child.
3. A dedicated approval wake qualifies only this action and current root, then automatically resumes the new start tool with the **durable exact approved payload**, even after idle/restart. Its native linkage is distinct from ordinary goal resume and cannot make the status tool or child callback action-capable. The server recomputes a digest over owner/project/root/profile, goal and control revision, current source ID/version, limits and expiry. An altered field, stale source, different SDK message, forged wake, rejected/expired/consumed decision, or replay holds. The existing approval table needs a narrow additive canonical bound-payload field for this action so restart does not depend on model memory or parsing display preview. The field stays local to agent approvals (SQLite); confirm the table is not mirrored to hosted Postgres. Never treat card text as machine authority.
4. After current rechecks, the server constructs the existing workflow admission and calls prepareWorkflowPlan. A narrow authorized issuance seam consumes the approved row and persists finite authority in one SQLite transaction/CAS; failure rolls both back. The human decision, not the model, supplies acknowledgesSoftTotalTokenAuthorization and acknowledgesCodingWorkflowCoverage. Existing source resolution, linking, dispatch, manager/reviewer membership, usage accounting, exact retry/unknown holds, checked criteria and quiescent stop remain the only execution path. Preserve idempotent partial-link holds without producing a second ordinal.

Use the existing approval table and a small additive bound-payload column, rather than a new proposal table. Store only the canonical compact proposal needed for digest verification and restart resume, with no source bytes, path, model transcript, or secrets. This is local SQLite agent state; verify the table's ownership before changing schema. Do not smuggle machine state into preview text.
