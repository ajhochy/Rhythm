# Phase 5 capability inventory — permissioned agent controls

Reference: Flutter from `origin/main` at `9fa2761ed78159f83f56982c03fcd85dc035039a`. React/API/fork evidence is from the current `codex/react-electron-live-suite` worktree on 2026-08-15. This compares executable capabilities, not test declarations.

## Missing in React/Electron

These are capabilities the shipping Flutter client has and the React/Electron client cannot perform against the live boundary today.

1. **Receive, recover, and resolve live permission requests exactly once.** Flutter renders real `permission.asked` cards, prevents double replies, retries a failed reply, gives destructive operations a confirmation path, and sends `once`, `always`, or `reject` through the dedicated reply endpoint (`origin/main@9fa2761:apps/desktop_flutter/lib/features/agents/views/_permission_card.dart:10-18,88-147,237-251`; `origin/main@9fa2761:apps/desktop_flutter/lib/features/agents/data/agents_data_source.dart:543-595`). React's visually similar card only mutates fixture state, while its live gateway has no permission method and its event reducer ignores permission frames (`apps/web/src/components/Transcript.tsx:22-34`; `apps/web/src/store.tsx:159-208,335-340`; `apps/web/src/gateway/sessions.ts:20-31`). No React live implementation found.

2. **Ask and answer the full live question shape.** Flutter renders an array of questions, option labels and descriptions, single- or multi-select behavior, optional custom answers, resolved-by-another-client state, and dedicated reply/reject calls carrying `answers: string[][]` (`origin/main@9fa2761:apps/desktop_flutter/lib/features/agents/views/_question_tool_card.dart:8-24,100-216,232-327`; `origin/main@9fa2761:apps/desktop_flutter/lib/features/agents/data/agents_data_source.dart:597-626`). React supports only one fixture prompt with `options: string[]`; answer and reject remain local mutations, and live events are ignored (`apps/web/src/types.ts:65-71`; `apps/web/src/components/Transcript.tsx:38-51`; `apps/web/src/store.tsx:159-208,337-340`). No React live implementation found.

3. **Persist a session's canonical permission mode.** Flutter reads and writes `default | acceptEdits | plan | bypassPermissions` on the session (`origin/main@9fa2761:apps/desktop_flutter/lib/features/agents/models/agent_session.dart:24-44,188-221`). React presents display labels such as “Accept Edits” and “Bypass” and changes only the selected local object; its gateway exposes no session-update method (`apps/web/src/components/Composer.tsx:161-164`; `apps/web/src/gateway/sessions.ts:20-31`). No React live implementation found.

4. **Review and cryptographically decide human approvals.** Flutter polls pending approvals, raises native notifications, focuses the originating transcript, shows action/preview/consequence, and signs approve/reject decisions with the approval nonce and payload digest (`origin/main@9fa2761:apps/desktop_flutter/lib/features/notifications/controllers/agent_approvals_controller.dart:8-10,29-135`; `origin/main@9fa2761:apps/desktop_flutter/lib/features/notifications/data/agent_approvals_data_source.dart:33-79`; `origin/main@9fa2761:apps/desktop_flutter/lib/features/agents/views/_human_approval_card.dart:8-12,97-158`). ## Capability families

### Permission and question handshakes

The API translates engine events before they reach either client. The permission card boundary is `permission.asked` with `sessionId`, `permissionID`, `directory`, `tool`, `patterns`, `title`, and `createdAt`; resolution is `permission.replied`. The reply route accepts only `reply: 'once' | 'always' | 'reject'` plus optional `message` (`apps/api_server/src/services/opencode_stream_bridge.ts:345-391`; `apps/api_server/src/controllers/agent_sessions_controller.ts:1369-1417`). Pending permissions are queryable after reconnect. This translated form—not an upstream event literal—is the renderer contract.

The translated question boundary is `question.asked` with `sessionId`, `requestId`, `callId`, and `questions`; the client replies by `callId` with `answers: string[][]` or rejects, and observes `question.resolved` (`apps/api_server/src/services/opencode_stream_bridge.ts:535-556`; `apps/api_server/src/controllers/agent_sessions_controller.ts:1423-1502`). Each question is `{header, question, options:[{label,description}], multiple?, custom?}` (`apps/opencode_fork/packages/opencode/src/question/index.ts:13-42,51-67`). React's current fixture types are not canonical boundary types.

### Human approval security

Approval status is `pending | approved | rejected`. Decisions require authenticated ownership, the `X-Rhythm-Human-Approval` header, and a signature bound to approval ID, session ID, status, `decisionNonce`, and `payloadDigest` (`apps/api_server/src/controllers/agent_approvals_controller.ts:118-186`; `apps/api_server/src/routes/agent_approvals_routes.ts:40-53`; `apps/api_server/src/security/human_approval_security.ts:13-15,60-72,127-152`). A visible Approve button without this signed route is not the capability.

### Delegation identity and isolation

Delegation accepts `callerAgentConfigId`, `targetAgentConfigId`, `prompt`, and trusted caller-session context. The service verifies owner, manager role, delegate roster, non-self delegation, workspace/profile scope, and maximum depth before creating a child (`apps/api_server/src/controllers/agent_delegation_controller.ts:14-30,55-65`; `apps/api_server/src/services/agent_delegation_service.ts:123-193,233-330`). Status intentionally exposes metadata, not child text: `delegationId`, `target`, `state`, `elapsedMs`, `durationMs`, `childState`, `childSteps`, `latestEvent`, `cancellable`, and `error` (`apps/api_server/src/services/async_delegation_status_service.ts:33-55,79-111`).

### MCP servers and profile policy

The MCP API returns server `name`, translated `status`, bounded `error`, redacted `environment`, `requiredEnv`, `needsCredentials`, `source`, and `tools`; lifecycle routes add local/remote configuration, credentials, OAuth status, connect, disconnect, and remove (`apps/api_server/src/routes/opencode_mcp_routes.ts:78-154,161-209,266-340,370-414`). Profile persistence uses `allowedMcpsJson`: `null` means unrestricted, an empty top-level list/map denies all, a server name grants that server, and a tools map grants exact named tools; malformed values fail closed (`apps/api_server/src/services/agent_profile_scope.ts:217-235,299-315`; `apps/api_server/src/services/mcp_dispatch_guard.ts:87-190`).

### Skills, commands, and deferred MCP dispatch

Skill list entries are `{name, description?, location, managed, source}`. Metadata carries `confidence`, `version`, lifecycle `status`, `source`, `uses`, scores, measurement reason, external-fork state, and environment readiness (`apps/api_server/src/routes/opencode_skills_routes.ts:89-142`). `allowedSkillsJson` is `null` for unrestricted and an exact-name array for restriction; `[]` denies all and malformed values fail closed (`apps/api_server/src/services/agent_profile_scope.ts:280-294,387-432`).

Command dispatch is a distinct WS frame `{v:1,type:'session.command',id,command,arguments}`, not prompt text (`apps/api_server/src/__tests__/opc_m3_4_command_dispatch.test.ts:104-176`; `apps/web/src/endpointMap.ts:110`). Deferred MCP policy is persisted as `mcpAllowlist: {servers:string[],tools:string[],deferredServers?:string[]}`. The fork exposes the bounded dispatcher catalog and rechecks the requested name against the session allowlist at execution time; an absent allowlist is unrestricted, while an explicit empty allowlist denies all (`apps/api_server/src/services/mcp_allowlist_expander.ts:5-25`; `apps/opencode_fork/packages/opencode/src/session/mcp_deferred_tools.ts:22-33,50-64,86-122`; `apps/opencode_fork/packages/opencode/src/session/mcp_allowlist.ts:15-39`). This backend capability exists, but React has no live catalog or structured tool journey with which to prove it.

## Inventory conclusion

React has a live profile CRUD path that can persist the four profile policy JSON fields, and the shared backend/fork already enforce scope and deferred dispatch. It does not have the live client domains needed to request, display, decide, configure, or inspect the nine capability groups above. Fixture cards, seeded catalogs, endpoint-map rows, and hard-coded slash suggestions are not evidence of a live capability.
