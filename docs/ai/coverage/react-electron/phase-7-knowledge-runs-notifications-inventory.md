# Phase 7 capability inventory — knowledge, runs, and notifications

Reference: Flutter at `origin/main` commit `9fa2761ed78159f83f56982c03fcd85dc035039a`.
React/Electron: current worktree. Phase source: `docs/ai/plans/2026-08-15-post-m1-parity-phases.md:136-146`.

This is a capability inventory, not a count of test declarations or endpoint-map rows. A React control that only changes component state and prints an HTTP-looking trace is not a live capability.

## Missing capabilities — Flutter has them; React/Electron does not

React seeds two memories and only filters/mutates the in-memory array (`apps/web/src/components/ToolWorkspace.tsx:105-130`). No React live memory implementation was found.

## Cross-cutting React/Electron finding

`ToolWorkspace` imports `useFixtures`, not `useGateway` (`apps/web/src/components/ToolWorkspace.tsx:1-6`). Its “request” footer is a local `Trace` object (`apps/web/src/components/ToolWorkspace.tsx:8,42-93`), and the file contains no `fetch` or gateway call. The live gateway domain type exposes only optional `tasks` and `sessions`, and `createLiveGateway` constructs only those two (`apps/web/src/gateway/index.ts:4-7,79-87`). Therefore endpoint-like strings in `ToolWorkspace` and `endpointMap.ts` are documentation/fixture evidence, not transport.

Electron likewise exposes only `gateway` configuration and `auth.signInWithGoogle` (`apps/electron/src/preload.cjs:9-22`). It currently supplies no privileged notification, secure approval-signing, filesystem-artifact opening, or knowledge/run bridge.

## Per-family detail

### Memory

- **Flutter:** Real local-API list/search/create/update/delete; explicit edit and clear-all UI; canonical provenance/trust/lifecycle fields. The repository owner filter returns the authenticated owner's rows plus instance-global owner-null vault rows (`apps/api_server/src/repositories/agent_memory_repository.ts:301-315,432-471`).
- **React:** Visually credible search/edit/delete fixture, but every operation is local state. Its `kind` option `decision` and `trust` values `verified`/`reviewed` are not the canonical persisted enums.
- **React cannot:** Prove captured memory survives reload/restart, retrieve an agent-captured row, enforce owner scope, expose source/verification records, or round-trip canonical IDs and lifecycle values.

### Research projects and runs

- **Flutter:** Full project input (`name`, `question`, `goals`, `domain`, `profileId`, `passConfig`, `modelPolicy`, `criticConfig`, `synthesisConfig`, `scheduleRef`, `budget`), owner-scoped runs, stage evidence, diagnostics, artifacts/sources/usage, cancel/resume/retry, magazine/export/discussion, and legacy retry fallback.
- **React:** Reduced local type with one run per project and display-only status. “Passes”, “Sources”, and “Statistics” tabs all point at the same local synthetic object.
- **API/transport:** `ResearchProjectRun.triggerType` is the closed union `'manual' | 'scheduled' | 'follow-up'`; its `status` is deliberately an open string (`apps/api_server/src/repositories/agent_research_repository.ts:37-90`). Owner ID is server-derived and every project/run lookup includes it (`apps/api_server/src/repositories/agent_research_repository.ts:244-270,416-440`).
- **React cannot:** Create or recover a real run, inspect source/artifact provenance, consume budget/usage/diagnostics, or navigate a discussion's returned session ID.

### Gallery

- **Flutter:** Real `AgentDesign` objects carry `artifactUrl`, `projectUrl`, `canvaUrl`, `artifactType`, `thumbnailUrl`, `sessionId`, and `createdAt` (`origin/main:apps/desktop_flutter/lib/features/agent_gallery/models/agent_design.dart:15-52`). Local artifacts use the server-owned `/agent-designs/:id/artifact` route rather than trusting a fixture path.
- **React:** Three constant cards. The open buttons do not open a URL or fetch bytes.
- **React cannot:** Browse newly generated designs, render authenticated previews, open actual deliverables/projects, or launch a real session with selected artifact context.

### Playbooks and cookbook

- **Flutter playbooks:** Engine catalog is authoritative; `source` distinguishes `command`/`mcp`/`skill`, while `managed` gates mutation. Managed content is `{name, frontmatter, template}` and frontmatter carries `description`, `agent`, `model`, and `subtask` (`origin/main:apps/desktop_flutter/lib/features/agent_playbooks/data/agent_playbooks_data_source.dart:13-64`).
- **Flutter cookbook:** Repository rows persist `title`, nullable `description`, serialized `stepsJson`, nullable `boundConfigId`, and server-derived `ownerUserId` (`apps/api_server/src/repositories/agent_cookbook_repository.ts:5-23`). Running a recipe returns a real local session ID.
- **React:** Both managers mutate constant arrays. Playbook refresh does not refresh the engine; cookbook execution fabricates a session via the fixture store.
- **React cannot:** Make a playbook appear in a real slash-command catalog, preserve managed/read-only provenance, or prove a recipe run is bound to its persisted recipe/config and observable session.

### Scheduled and delegated execution

- **Flutter:** Real CRUD/enable/trigger for daily/weekly/monthly/cron/once tasks, profile and MCP/skill constraints, next/last run state and error, plus real linked session history.
- **API:** Scheduling is local SQLite execution state. The hosted Postgres process refuses to advance/fires none and logs stranded enabled rows (`apps/api_server/src/services/agentSchedulerService.ts:769-799`). On local restart, stale `running`/`queued` tasks are reset to error rather than left falsely active (`apps/api_server/src/services/agentSchedulerService.ts:799-851`). Durable run rows preserve `taskId`, attempt times, `status`, `error`, and `rootSessionId`.
- **Delegation:** A child is allowed only when the caller session belongs to `authenticatedUserId`, depth stays at most 2, caller is a manager, and the target is in `allowedDelegatesJson`; async success is `{sessionId,sdkSessionId,status:'dispatched',message,targetAgentConfigId}` (`apps/api_server/src/services/agent_delegation_service.ts:13-35,38-61,138-179,248-285,345-387`).
- **Gap discovery:** Capability-gap work is debounced, bounded by `maxGapsPerPass`, separately budgeted, agent-execution-role gated, and returns `gapsConsidered`, `skipped`, and optional `skippedReason` (`apps/api_server/src/services/gap_discovery_scheduler.ts:51-73,95-116,118-130`).
- **React cannot:** Persist or execute a schedule, show truthful post-restart state, distinguish copied/disabled sandbox rows, prove ownership/profile/permission gates, or show a durable root run tree.

### Run status and quality evidence

- **Flutter:** Scheduled session history and research runs expose actual statuses/errors/progress. The report card distinguishes quality from spend and refuses misleading rates when history is thin.
- **API:** Run-quality's canonical response is a read-only owner-scoped rollup; `notEnoughData` forces rate fields null, while `unmeasuredRuns` prevents unknown outcomes from silently becoming passes (`apps/api_server/src/services/run_quality_service.ts:14-61,201-246,277-287`).
- **React:** Synthetic `completed`/`error` rows and hard-coded percentages. No real evidence is fetched.
- **React cannot:** Explain which session/run produced a metric, show truthful null/unmeasured states, or prove completion/failure/status recovery against persisted records.

### Notifications and native presentation

- **Creation:** Server-side domain events persist canonical rows through `NotificationService`; actor-self notifications are suppressed where applicable and step-completion fans out to collaborators (`apps/api_server/src/services/notification_service.ts:6-89`). Agents may POST `{title,body}` to `/notifications/agent`; the API stores the row and broadcasts `{v:1,type:'notification.push',id,title,body}` (`apps/api_server/src/controllers/notifications_agent_controller.ts:6-32`; `apps/api_server/src/app.ts:155-157`).
- **List/read isolation:** `/notifications` requires auth. List and updates always bind `recipient_user_id` to `req.auth.user.id` (`apps/api_server/src/routes/notifications_routes.ts:5-13`; `apps/api_server/src/controllers/notifications_controller.ts:7-34`; `apps/api_server/src/repositories/notifications_repository.ts:56-119`).
- **Flutter:** Handles both persisted domain notifications and transient agent push notifications, folds pending approvals into its badge, marks domain rows read, routes targets, and presents native macOS banners.
- **React/Electron:** A static menu only. React's live WebSocket handler processes session events but has no `notification.push` branch (`apps/web/src/store.tsx:161-200`). Electron has no native notification permission/presentation/activation bridge.
- **React/Electron cannot:** Receive agent notification creation, maintain recipient-scoped unread state, deduplicate delivery, mark actual rows read, navigate owned targets, show approval actions, present a native banner, or recover the target after a notification launches the packaged app.

## Inventory conclusion

React currently has strong fixture sketches for most Phase 7 screens, but only two live gateway domains exist and none covers knowledge, research, Gallery, playbooks, cookbook, schedules, run quality, notifications, or approvals. Electron adds no native-notification or approval-signing contract. Phase 7 is therefore a live-capability build, not a test-mapping cleanup.
