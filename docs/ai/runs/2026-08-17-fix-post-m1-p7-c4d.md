## Notes

AJ asked to fix the one remaining honest gap from tonight's parity work: `post-m1-p7-c4d`
(approve/reject on a pending human approval sends a real P-256 decision signature, not a rejection).

Researched first (Explore agent, not summarized here — see the agent's report in-session):
`apps/api_server/src/security/human_approval_security.ts` verifies ECDSA P-256/SHA-256 over a
canonical `'rhythm-human-approval-v1\n{approvalId}\n{status}\n{decisionNonce}\n{payloadDigest??''}'`
string, DER-encoded signature, against a public key from `HUMAN_APPROVAL_PUBLIC_KEY` (env var, raw
65-byte SEC1 point). The Flutter reference (`human_approval_signer.dart` +
`HumanApprovalSigner.swift`) does this via a native `SecKey` (Secure-Enclave-when-available) behind a
narrow platform channel, with Flutter self-generating a capability secret and injecting both it and
the public key into the `api_server` child process's environment at spawn time — since Flutter
literally spawns that process itself.

Chose Web Crypto (`SubtleCrypto`) over an Electron-main/Keychain IPC bridge for one concrete reason:
`post-m1-phase-7-approvals.redspec.ts` runs the renderer as a plain Playwright/Chromium page with no
Electron main process attached (confirmed by reading the test and its harness — no `window.rhythmShell`
mock exists), so only a signer that works in an ordinary browser tab could ever make that test pass.
Web Crypto is also literally the correct choice architecturally: this same renderer runs unmodified as
a plain browser page and inside packaged Electron, and `SubtleCrypto` ECDSA works identically in both.

One real interoperability bug caught before it shipped: Web Crypto's ECDSA output is raw IEEE P1363
(`r || s`, 64 bytes), never DER — Node's `crypto.verify` (what the server uses) requires DER. Wrote a
small hand-rolled DER integer encoder (`derInteger`/`p1363ToDer` in the new module) rather than
pulling in a dependency for two dozen lines of ASN.1.

Honest, documented gap left open (see the module's doc comment and `project-state.md`): the
self-generated key/capability are not yet synchronized with a real server's environment, because
`apps/electron` doesn't spawn `api_server` the way Flutter does. Closing that fully means either
Electron owning the server's process lifecycle (a bigger change) or a new server-side enrollment
endpoint — flagged as real follow-up work, not faked here.
