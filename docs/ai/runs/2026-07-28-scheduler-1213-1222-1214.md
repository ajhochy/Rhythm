## Notes

- Root cause for #1222's "startup burst" was traced precisely: `startAgentSchedulerJob()`'s immediate catch-up `checkDueTasks()` call fires before `opencodeClient.initialize()` is even invoked in `server.ts` (a separate, later, non-blocking `.then()` chain) — not merely a slow cold start.
- An earlier version of the #1222 readiness-wait lived inside the shared `AgentRunner._runOnce()` (fixing it "once" for every caller). Discovered via a full-suite regression (`skill_extractor.test.ts` timing out) that this made EVERY unmocked-engine call to `run()` wait up to 90s before failing — collateral damage for any test or genuinely-broken-engine scenario outside the scheduler's specific boot race. Relocated the wait to the one call site that actually races boot (`agentSchedulerService.ts`), eliminating the regression while still fixing the described bug.
- #1214's root cause: the hosted production deployment's own `.env.production.example` never set `RHYTHM_ROLE`/`DB_CLIENT` explicitly (defaulted to `all`/`sqlite`-looking-but-Postgres-configured), and the scheduler's dispatch branch (`env.agentLocal`) never gated *whether* to tick, only *how*. Fixed by gating on `env.dbClient` (already the established local/hosted signal in this file) instead.
