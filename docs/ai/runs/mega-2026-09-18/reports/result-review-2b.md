Findings:
- [critical] BLOCKER — Hermes exposes the session credential to a persistent renderer (apps/electron/src/hermes-view.mjs:133-141)
  Issue #1542 and the explicit review constraint prohibit the token from reaching renderer-held or persistent state. The view nevertheless selects `persist:rhythm-hermes` and documents that the child injects the token into its HTML; the integration contract confirms it becomes `window.__HERMES_SESSION_TOKEN__`. AJ will be able to open the dashboard renderer’s DevTools and observe the session credential in the page global, while its persistent partition unnecessarily retains browser state.
  Recommendation: Use an ephemeral partition and a server/native authentication handoff that is unavailable to page JavaScript, then prove in real Electron that globals, storage, preload, status, URLs, and logs contain no token.
- [high] MAJOR — Any HTTP error is treated as successful Hermes readiness (apps/electron/src/hermes-server.mjs:216-223)

AJ can smoke this by returning 503 from the endpoint: Rhythm will report Ready and attempt to attach the view anyway.
  Recommendation: Require an expected success status and validated Hermes-specific response, preferably authenticated and tied to the owned child, before publishing `ready`.
- [high] MAJOR — The required new-chat typed intent is explicitly rejected (apps/electron/src/hermes-view.mjs:241-253)

  Recommendation: Implement document-bound draft prefill through the constrained channel and add a real Electron test proving the text appears editable and is never auto-sent.
