## Findings / smallest fixes

1. **P1 — Progress refresh failure removes the usable interface and stays latched after recovery.** `ToolWorkspace.tsx:916-922,963`; incumbent `ListInspector.tsx:56-57,160,189,201`. Poll failures enter the fatal list `error` prop, removing rows and inspector (including persisted progress). A later successful poll updates tasks but never clears that error. Smallest correct fix: give background refresh a nonfatal inline/live error while retaining last-known tasks/progress, and clear that error on successful refresh. Add an intercepted failing GET followed by recovery assertion that the selected schedule and progress remain available.

2. **P1 — Selection switching exposes incorrect enabled/loading state for overlapping requests.** `ToolWorkspace.tsx:830-832,895-907,980`. The synchronous per-task Set protects POST dedupe, but rendered busy state uses a single `triggeringId`. Hold A, switch to B, trigger B, then switch back: A renders enabled/not Queueing while still pending. Either completion clears the busy indicator for the other request. The single error slot also allows B's request to clear/overwrite A's error. Smallest fix: render busy and error state keyed by task ID, updating/removing only the completing task. Preserve the synchronous guard. Assert A/B switching with held requests resolving in both orders, task-specific errors, disabled state and one POST per task.

3. **P1 — Immediate pending state lacks a dedicated accessible announcement.** `ToolWorkspace.tsx:896,980-984`. Before acceptance, only the disabled button's label changes to Queueing; the status paragraph still shows the previous run or is absent. Changing a disabled button's accessible name is not a reliable live status announcement (WCAG 2.1 AA 4.1.3 review concern). Smallest fix: keep a mounted status region and update it immediately to Queueing, then queued/running/terminal; expose busy state on the relevant region. Native button keyboard semantics and focus-visible CSS are present, but actual keyboard/focus retention and assistive-technology announcements are unverified, not certified failures or passes.

4. **P2 — Several visible errors are not actionable.** `gateway/schedules.ts:89-90,95-107`; `ToolWorkspace.tsx:903-904,982`; spec `:48-50,60-62`. Authentication required, Forbidden, generic 503 and Schedule service unavailable identify a problem without telling the user what to do. Re-enabled Trigger now is not a tested successful retry. Retired configuration text is actionable and preserved; locked configuration identifies review required. Smallest fix: retain nondisclosing error handling but add safe next steps (sign in, request access, service/connectivity check then retry). For an ambiguous network failure, refresh persisted state before encouraging a new trigger. Assert aborted transport, profile failure and actual second-click recovery, not only re-enablement.

5. **P2 — Rendered acceptance evidence is narrower than the UI acceptance.** `tests/regressions-manual-trigger.spec.ts:6-43,45-63`; config `:5-15`; contract `:40-45`. Existing cases cover held loading, one POST, disabled queued/running, reload, one successful no-op terminal, recurrence-off label and five HTTP errors. They do not assert status/alert roles or announcements, keyboard Enter/Space/focus, selection switching, actual retry, aborted network, progress polling failure/recovery, failed terminal outcome or route-away/reopen. The disabled synthetic DOM click is a legitimate suppression check, not a rapid keyboard/pointer sequence. Smallest evidence fix: extend the owned fixture cases for these behaviors; do not relabel them actual-engine or installed-package proof.
