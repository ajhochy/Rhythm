## Notes / blocker

Dispatch requires the session share flow to review the **exact snapshot/content**, reuse current APIs, and report an unusable current route shape before changing backend handlers.

The existing share creation route cannot bind publication to the reviewed content:

1. `apps/api_server/src/controllers/shared_transcripts_controller.ts:72-93` validates `review.items`, then selects current source items by requested **ID only**. Submitted category/content do not participate in the snapshot. There is no expected source revision/hash or review token check.
2. `apps/api_server/src/repositories/shared_transcripts_repository.ts:118-160` re-reads the current persisted `parts_json` and derives review items at creation time.
3. `apps/api_server/src/services/transcript_share_sanitizer.ts:160-199` derives stable part IDs and sanitizes the current selected items. Thus an item can keep its ID while its content changes after the user reviewed it.
4. `apps/api_server/src/routes/shared_transcripts_routes.ts` exposes create, list, read, and revoke, but no prepare/finalize snapshot binding. The GET/DELETE share routes operate on an already-created share.

Concrete failure sequence supported by the source: review part `p` containing `approved text`; a streaming or concurrent update persists `unreviewed text` under `p`; submit the reviewed `p`; the server publishes sanitized `unreviewed text` to named recipients. This is a source-level finding, **not an executed reproduction**.

A client-side re-read still leaves a race before POST. Comparing the returned share and revoking a mismatch happens after publication, so it cannot guarantee that unreviewed content was never exposed. Reimplementing the sanitizer or inventing a renderer snapshot token would not supply an authoritative server precondition.

Other API observations (not additional blockers): real todos exist at `GET /agent-sessions/:id/todo`; provenance at `GET /agent-sessions/:id/memory-provenance`; structured history is paginated at `GET /agent-sessions/:id/messages`; MCP retrieval is URI-free at `GET /agent-sessions/:id/mcp-app-resource/:callId`. `/users` is an unscoped directory, not proof of recipient eligibility; existing `/workspaces/me/members` should be evaluated for the authoritative owner-workspace case rather than inventing a directory API.
