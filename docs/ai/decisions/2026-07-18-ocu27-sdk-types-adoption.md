# OCU-27: adopted real v1/v2 SDK types where genuinely covered; kept the hand-written d.ts (not a `file:` dep, not a full re-export)

## Context

Issue #1068 asked to (a) choose between a `file:`/workspace dep on the fork's
regenerated SDK vs. shrinking the hand-written `opencode-ai-sdk.d.ts` to a
re-export shim, and (b) convert named direct-fetch shims in
`opencode_client_service.ts` to typed SDK calls where the regenerated client
covers them.

Two things this run discovered that the issue text didn't anticipate:

1. **`apps/opencode_fork/packages/sdk/js` (both `src/gen` legacy and
   `src/v2/gen`, the latter regenerated by #1067) ships only unbuilt ESM `.ts`
   source — no `dist/`, and its own `package.json` `exports` point straight at
   `.ts` files.** There is nothing to consume, at runtime or as a type source,
   without adding a build step for it — which AGENTS.md explicitly forbids
   ("do NOT add apps/opencode_fork to apps/api_server/tsconfig.json or any
   existing build pipeline").
2. **The REAL, already-installed npm dependency `@opencode-ai/sdk@1.14.49`
   (root `node_modules/@opencode-ai/sdk`, hoisted via the npm workspace — a
   real built package, distinct from the fork subtree) ships a fully-built
   `dist/v2/gen/*.d.ts` in addition to the default v1 `dist/gen/*.d.ts`.** The
   v2 export genuinely covers `question.list/reply/reject` and `app.skills()`
   (with `content`) — endpoints the v1 export (what api_server currently
   imports) does not expose. Verified directly against
   `node_modules/@opencode-ai/sdk/dist/v2/gen/{sdk,types}.gen.d.ts`.

## Decision

**(a) `file:` dependency on the fork: REJECTED.** Confirmed via direct
inspection — no `dist/`, ESM-only unbuilt source, would either not resolve at
all or require violating the "don't build the fork" rule for zero benefit
(the real npm package already ships the equivalent generated types, more
authoritatively, for anything upstream opencode supports).

**(a, cont'd) Full re-export from the real generated `.d.ts` in place of the
777-line hand-written union: REJECTED**, based on a direct empirical probe
(temporarily replaced the whole file with `export * from
'@opencode-ai/sdk/dist/index'` and ran `tsc`). Concrete, provable breakage
across 8 files (`agent_runner.ts`, `agent_sessions_controller.ts`,
`opencode_stream_bridge.ts`, `agent_profile_sync.ts`, `opencode_mcp_routes.ts`,
4 test files) because the REAL generated schema:
- Has no `permission.asked`, `question.asked`, `question.replied`,
  `question.rejected`, or `message.part.delta` event variants — these are
  real wire events the RUNNING engine emits (confirmed empirically by prior
  agents, per the file's own comments) that the officially-generated OpenAPI
  schema never documented. A blind swap would silently drop handling for
  them — exactly the regression class AGENTS.md's #948 postmortem warns
  about.
- Models `Message` as a `UserMessage | AssistantMessage` discriminated union
  with no shared flattened `.parts` field, breaking existing `.parts` access
  patterns.
- Has no `SdkAgent`, `McpStatusEntry`, `PartInput`, `McpLocalConfigInput`,
  `McpRemoteConfigInput` names — Rhythm-authored convenience aliases.

Swapping wholesale would touch call sites well outside this issue's assigned
file (`opencode_client_service.ts`) and risk exactly the kind of regression
the coding-agent discipline (smallest correct change) and the AGENTS.md
behavioral gate exist to prevent. **Kept the hand-written ambient module as
the source of truth** (satisfies the issue's explicit non-goal: "KEEP the
ESM/CJS dynamic-import bridge pattern as-is" — the module's necessity for
bare-specifier type resolution is unrelated to whether its content is
hand-written or re-exported).

**(b) Adopted real generated types narrowly, in two places:**

1. **`pty` namespace** — added `Pty`/`client.pty.{create,update,remove}` to
   the ambient d.ts, sourced directly from the real, already-installed
   `node_modules/@opencode-ai/sdk/dist/gen/{sdk,types}.gen.d.ts` (v1, default
   export — this endpoint IS covered there). Removed all three
   `(client as any).pty.*` casts in `opencode_client_service.ts`.
2. **v2 client for genuinely-covered shims** — added a second ambient module
   `declare module '@opencode-ai/sdk/v2/client'` (narrow, hand-authored,
   verified line-by-line against the real `dist/v2/gen/*.d.ts`) and a
   `v2Client()` helper (mirrors the existing v1 dynamic-import pattern:
   `new Function('s','return import(s)')`, same ESM/CJS bridge, not cached
   long-term so a `reloadCredentials()` bounce is picked up). Converted:
   - `listSkills` / `listSkillsWithContent` → `client.app.skills({directory})`
     (one v2 call now backs both methods; `content` was already in the real
     response shape).
   - `listQuestions` → `client.question.list({directory})`.
   - `replyToQuestion` → `client.question.reply({requestID, answers, directory})`.
   - `rejectQuestion` → `client.question.reject({requestID, directory})`.

   These construct the exact same HTTP requests (`GET /skill`, `GET
   /question`, `POST /question/{id}/reply`, `POST /question/{id}/reject`) the
   prior raw-fetch calls used — a client-side typing change, not a
   wire-protocol change. Removed the now-dead private `questionAction` helper.

**Left as direct-fetch (confirmed genuinely uncovered, in NEITHER the real
npm package NOR the fork's regenerated v2 schema — these are Rhythm's own
unpublished engine patches, not upstream opencode features):**
- `updateSessionAllowlist` / `updateSessionSkillAllowlist` — `mcpAllowlist`/
  `skillAllowlist` are absent from `SessionUpdateData` in both sources.
- `reloadSkills` (`POST /skill/reload`) / `reloadConfig` (`POST
  /config/reload`) — absent from both sources; only the FORK's own
  regenerated (unbuilt) v2 schema has a `Skills.reload`/`Config.reload`
  method, which per the rejection above is not consumable.

## Alternatives considered

- Migrate the WHOLE client from the v1 default export to v2 (v2 covers
  everything v1 does, plus more): rejected as far exceeding "smallest correct
  change" for a single issue — v2's calling convention is a flat-parameter
  object per method (not v1's `{path,body,query}` split), so every one of the
  ~30 existing v1 call sites (session lifecycle, mcp management, auth,
  prompt/promptAsync, etc.) would need re-verification against the v2 shape.
  Flagging as a good, bounded follow-up issue: "migrate api_server's opencode
  client wholesale to the v2 SDK export," since v2 would let the remaining
  direct-fetch shims (skill.reload, config.reload, mcpAllowlist/skillAllowlist
  once the fork's schema is eventually built/published) be converted too.
- Wiring a build step for the fork's `packages/sdk/js` so its regenerated
  v2 types become consumable: rejected — explicitly forbidden by AGENTS.md's
  vendored-subtree rule, and out of scope for this issue.

## Consequences

- `opencode-ai-sdk.d.ts` grew (777 → ~900 lines: +pty +v2 client block) rather
  than shrinking to a bare re-export shim, contrary to the issue's literal
  phrasing. The acceptance criterion "hand-written union gone (or reduced to
  a re-export shim)" is **not** met in the wholesale sense; it IS met in the
  narrow sense that adds pty + v2, both sourced from real generated types
  rather than hand-guessed reconstructions, and `tsc --noEmit` is clean.
- Zero `(client as any)` remain in `opencode_client_service.ts` (verified by
  grep) — that specific acceptance criterion IS met.
- `updateSessionAllowlist`/`updateSessionSkillAllowlist`/`reloadSkills`/
  `reloadConfig` remain direct-fetch, confirmed correct per the issue's own
  instruction ("If a given endpoint is NOT in the regenerated client, LEAVE
  its direct-fetch shim as-is").
- If Rhythm's fork-only engine patches (mcpAllowlist/skillAllowlist,
  skill.reload, config.reload) are ever published as a real, built npm
  version (or the fork gets a `dist/` build step approved for a future
  issue), those four methods become the next SDK-adoption candidates.
