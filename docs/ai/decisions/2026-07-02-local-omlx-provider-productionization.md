# Productionize the local oMLX provider (#868)

## Context

A manual proof-of-concept had been hand-wired into the live machine's
`~/.config/opencode/opencode.json`: an `omlx` provider entry (oMLX 0.4.4
serving `mlx-community/gpt-oss-20b-MXFP4-Q8` on
`http://127.0.0.1:8000/v1` via the generic `@ai-sdk/openai-compatible`
loader) plus a `local` agent whose `tools` map disabled every MCP server,
`skill`, `task`, `webfetch`, and `websearch` — dropping tool-schema prefill
from ~136K to ~9K tokens, which is what makes local inference viable at all
on a 32GB Apple Silicon Mac. Issue #868 asked for this to be productionized:
generated by Rhythm code (not hand-edited), optional, non-machine-specific,
and validated beyond "it generates text" (a prior local-model candidate,
Qwen3-Coder-30B, was rejected because it emitted textual
`<function=...>` markup instead of real structured tool calls).

The branch already carried the pattern to follow: `ensureGeminiProjectConfig()`
in `gemini_project_config.ts` (idempotent read-modify-write of
`opencode.json`, called from `opencode_client_service.ts`'s `_initializeImpl`
before the engine spawns) and a previously-landed local Ollama provider
(`KEYLESS_LOCAL_PROVIDER_IDS`, `ROUTE_FALLBACKS_BY_AGENT.opencode` in
`agent_model_resolver.ts`, `local_ollama_provider.test.ts`).

## Decision

- New module `apps/api_server/src/services/local_omlx_provider.ts` owns two
  concerns:
  - `ensureOmlxProviderConfig()` — idempotently writes `provider.omlx` +
    `agent.local` into `opencode.json`, gated entirely behind
    `env.omlxProviderEnabled` (`RHYTHM_LOCAL_OMLX_ENABLED=true`). Off by
    default; when off, the function does not touch the filesystem at all.
    Called from `opencode_client_service.ts` Phase 3b, immediately after the
    existing Gemini projectId step and before `createOpencode()` spawns the
    engine (same ordering constraint: the engine reads `provider`/`agent`
    once at startup).
  - `buildLocalAgentPermission()` — the constrained tool surface, expressed
    as opencode's own `permission` schema (`read/glob/grep/list/edit/bash:
    'allow'`, `task/webfetch/websearch/skill: 'deny'`, plus a `'*': 'deny'`
    catch-all for MCP tool names). Chose `permission` over the deprecated
    `tools` map (which the manual POC used) because the fork's own
    `ConfigAgent.normalize` documents `tools` as deprecated in favor of
    `permission` — no reason to productionize the deprecated shape.
  - `detectAndUnloadCompetingOllamaModel()` — runs `ollama ps`, and if the
    configured competing model (`env.omlxCompetingOllamaModel`, default
    `qwen3.6-work` — matching the model already wired into
    `agent_model_resolver.ts`) is loaded, runs `ollama stop <model>`.
    Never throws (Ollama not installed is the common/happy case), and
    surfaces the exact manual action via a warning log when auto-unload
    isn't possible or fails.
- New module `local_omlx_tool_call_smoke.ts` provides
  `hasStructuredToolCall()` (pure — asserts a real `tool_calls` entry exists
  and explicitly detects the textual-markup failure mode via regex) and
  `runOmlxToolCallSmoke()` (a live two-turn tool-call-then-tool-result round
  trip against a real OpenAI-compatible endpoint, for manual verification
  once oMLX is actually installed — not run in CI).
- `agent_model_resolver.ts`: `omlx` added to `PROVIDER_TO_AGENT_KIND` (maps
  to the generic `opencode` kind, same as `ollama`) and appended LAST to
  `ROUTE_FALLBACKS_BY_AGENT.opencode` — after both the cloud route
  (openrouter) and the existing Ollama route — so `resolveModelForAgent`
  only ever reaches it when nothing else is authed. It is fully selectable
  (a normal profile once the config is written) but never auto-picked ahead
  of any existing default.
- `env.ts`: all machine-variable values (endpoint, model id, context/output
  limits, competing-Ollama-model name) are env-derived with documented
  defaults — no literal username or home-directory path anywhere in the
  generated config or the code that writes it. `homedir()` is used only to
  locate the shared `~/.config/opencode/opencode.json` path, identical to
  every other config-patcher in this codebase.

## Alternatives considered

- **Write a `.md` agent file under `~/.config/opencode/agents/local.md`**
  instead of an `agent.local` top-level JSON entry. Rejected: the fork's
  `config.ts` merges `.md`-derived agents with the top-level `agent` object
  either way (`mergeDeep`), and every existing Rhythm-owned config mutation
  (`ensureGeminiProjectConfig`, `ensureRhythmMcp`, `disableStandaloneMemoryMcp`)
  patches `opencode.json` directly — staying consistent means one file format
  to reason about, and no new file-write path.
- **Seed a DB row directly into `agent_configs` for `local`.** Rejected:
  `syncOpencodeAgentProfiles()` already mirrors every engine-reported agent
  (from `opencode.json`'s `agent` block, merged with any `.md` files) into
  `agent_configs` on its normal cadence. Writing `agent.local` into
  `opencode.json` is sufficient — the existing sync machinery picks it up
  with no new code path, and it stays consistent with how the Ollama route
  already appears without any special-cased DB seed.
- **Auto-unload Ollama unconditionally.** Rejected: `autoUnload` defaults to
  `true` (matching the issue's "better, automate the detect+unload"
  preference) but is an explicit parameter so a future caller (e.g. a UI
  banner flow) can request detect-only surfacing without stopping a model
  a user may still be actively using elsewhere.

## Consequences

- Enabling oMLX is a single env var (`RHYTHM_LOCAL_OMLX_ENABLED=true`) plus
  having the oMLX app actually running locally — no code change needed
  per-machine.
- The `local` agent profile will appear in `agent_configs` (and therefore
  the composer picker) automatically once `syncOpencodeAgentProfiles()` next
  runs after the flag is enabled and the engine restarts — no separate
  seed/migration was added.
- Follow-up (explicitly out of scope for #868, flagged here): no automated
  CI check exercises `runOmlxToolCallSmoke()` against a real server (Apple
  Silicon + oMLX app required); it must be run manually once the app is
  installed on a target machine. The unit-testable assertion logic
  (`hasStructuredToolCall`) IS covered automatically.
- Follow-up: `detectAndUnloadCompetingOllamaModel()` only checks the one
  configured model name; a machine running a differently-named large Ollama
  model would need `RHYTHM_LOCAL_OMLX_OLLAMA_MODEL` set accordingly (or a
  future enhancement to unload ANY running Ollama model above a size
  threshold, not just a named one).
