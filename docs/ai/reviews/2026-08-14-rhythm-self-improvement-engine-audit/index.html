Rhythm Self-Improvement Engine Audit

Rhythm has a strong safety-oriented foundation, but it is not yet a reliable self-learning system.

Today it behaves more like telemetry → heuristic/LLM suggestions → occasional mutation → narrow proxy check than observed user outcome → causal diagnosis → controlled experiment → durable measured improvement → learned policy.

What this means

Rhythm currently gets busier as it is used, but does not consistently get smarter.

Approve none of the 25 current proposals as written. Put the optimizer in shadow mode while the evidence, lifecycle, and measurement loop is repaired.

Filter the implementation plan

P0 · contain now

Immediate containment

Stop the system from converting weak evidence into production changes. Keep observation running, but separate learning from mutation.

  1. Disable automatic scope prune/tighten

    Why now69 of 109 active proposals are scope tightening/pruning; observed tool aliases caused false “unused” findings; 29 of 46 checked scope removals were contradicted by actual tool calls (63%).

    ImplementationHard-disable low-risk auto-apply for tighten-scope and prune-scope; require canonical capability evidence and human review.

    Exit gateNo scope removal promotes unless canonical tool identity proves zero use over a defined observation window and task replay shows no regression.

  2. Quarantine and supersede the current queue

    Why nowIndependent audit graded 0/25 approvable, 11 unsupported/no-op, 12 harmful, and 2 needing re-authoring.

    ImplementationReject or supersede current proposed rows with a machine-readable reason; preserve evidence for regression tests; re-enter only as fresh hypotheses.

    Exit gateEvery regenerated proposal cites source events, target state hash, expected outcome, experiment, and rollback rule.

  3. Run the optimizer in shadow mode

    Operating modeContinue observation and proposal generation, but do not mutate production state.

    ImplementationScore proposal precision against human adjudication and controlled replay outcomes.

    Exit gateSustained precision threshold, zero silent high-severity regressions, and clean lifecycle reconciliation before any auto-apply family is re-enabled.

  4. Exclude internal/self-improvement sessions from harvesting

    Why nowEvaluator, smoke, measurement, scheduled, and self-improvement sessions contaminate learned skills and signals.

    ImplementationClassify provenance at ingestion and exclude internal run families before feature extraction or skill harvesting.

    Exit gateProvenance filters are enforced at ingestion and covered by tests.

P1 · repair evidence

Make every diagnosis reproducible

A proposal should carry enough structured evidence to reproduce the diagnosis, detect drift, and refuse unsafe execution.

Canonical capability identity

Problem

MCP server IDs, operation IDs, aliases, and tool names fragment one capability into several identities.

Change

Normalize every representation into one capability ID before gap, scope, and usage calculations.

Proof

Alias-equivalent calls resolve to one identity and do not generate false gaps or removals.

Behavioral retry telemetry

Problem

Keyword counts confuse discussion of retry policy with actual retry behavior.

Change

Capture attempt spans, tool errors, recovery transitions, repeated equivalent calls, and unresolved failure signatures.

Proof

Successful outputs discussing “retry policy” do not create retry-loop proposals.

Evidence bundles

Problem

Reviewers cannot reconstruct why a proposal exists from the proposal alone.

Change

Attach immutable source event IDs, observation window, counter-evidence, target snapshot/hash, confidence calibration, and expected user outcome.

Proof

Reviewers reproduce the diagnosis from the proposal alone.

Freshness and conflict control

Problem

Stale proposals can mutate drifted targets or roll back over newer state.

Change

Add expiry, optimistic concurrency, target hashes, mutation locks, stale/no-op detection, and conflict/supersession rules.

Proof

Drifted targets cannot be applied or rolled back over newer state.

Lifecycle reconciliation

Problem

Observed state: 248 total, 109 active, 80 rejected, 27 reverted, 25 proposed, 5 measuring, and 2 stuck at applied.

Change

Repair stale active, applied, and measuring rows; make one state machine authoritative.

Proof

Every row reconciles to an allowed transition with one authoritative status.

P2 · make learning causal

Replace proxy success with measured task improvement

The system should earn promotion through controlled evidence—not through a smaller allowlist, a textual score, or the absence of an immediate error.

  • Replace immediate proxy checks with task-level baseline vs candidate experiments.
  • Define outcome metrics per proposal family before generation: task success, correction rate, latency, cost, tool failures, user acceptance, and regression set.
  • Require minimum sample size or controlled replay; label inconclusive results rather than treating them as success.
  • Feed reverts, regressions, approval decisions, and structured rejection reasons back into generator evaluation.
  • Treat active as “deployed,” never “proven”; only measured user-outcome improvement earns verified promotion.
  • Create family-specific measurement harnesses instead of one generic evaluator.

Do

  • Verify task outcome improvement.
  • Run controlled baseline/candidate comparisons.
  • Capture structured human decision reasons.
  • Promote only after measurable benefit.

Don’t

  • Count textual mentions of retry as retry behavior.
  • Treat a smaller allowlist as proof of improvement.
  • Treat active or a high textual score as proven value.
  • Bulk approve the live queue.
P3 · grow safely

Make utility—not collection—the promotion gate

Keep external adoption human-gated. Treat harvested and external skills as candidates until reuse and task benefit are observed.

  • Gate skill extraction on successful, user-relevant sessions with clean provenance.
  • Deduplicate against existing capabilities before creating a draft.
  • Sandbox external candidates; require stack relevance, security review, and task replay.
  • Promote a harvested or external skill only after observed reuse and benefit; archive candidates that never demonstrate utility.
  • Keep external adoption human-gated.

Release checklist

Definition of “getting smarter”

  • Proposal precision is measured against human adjudication and exceeds an agreed threshold for a sustained window.
  • No stale active, applied, or measuring lifecycle rows.
  • Every measurement references a real task outcome or controlled replay.
  • Every mutation has target hash, lock, expiry, rollback, and conflict protection.
  • Reverts and rejection reasons influence future proposal scoring and generation.
  • Harvested skills demonstrate reuse and measurable benefit before promotion.
  • Auto-apply is enabled per proposal family, not globally, only after that family passes regression gates.

North star: verified user-outcome improvement per promoted change—not proposal count, artifact count, or smaller allowlists.

Preserve

Keep the safety-oriented foundation

Repair the learning loop without discarding controls that already fail safely or preserve reversibility.

  • Centralized risk classifier; unknown proposal kinds fail closed to high risk.
  • Human gate for external code and capability adoption.
  • Privileged change shapes override misleading low-risk labels.
  • Revalidation at approval time.
  • Before snapshots and rollback paths.
  • Proposal state machine and per-run generation/model-call caps.
  • Attempt-aware re-diagnosis exists for some reverted proposals.

Two observed retry-loop false positives
Example 01 · PCO sync

A completed PCO sync task contained ordinary discussion of HTTP retry policy; keyword matching found 13 “retry” mentions and generated a one-line “reduce retry loops” recipe despite successful delivery.

Example 02 · issue writing

A successful issue-writing session discussed selective retry/resume features; 15 textual matches produced another retry-loop proposal even though the agent loaded its skill, used task tracking, recovered from one missing template, and delivered the requested issues.
