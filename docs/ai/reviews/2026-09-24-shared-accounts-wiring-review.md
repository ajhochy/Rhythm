## Concrete source gaps that must be addressed

1. **Document origin mismatch.** `main.mjs:196-201` owns `rhythm://app/index.html`, whose URL origin is `null`. S2 `validateGrantMutationRequest` requires `new URL(sender.senderUrl).origin === context.serverOrigin`, an HTTP(S) API origin. A legitimate document cannot satisfy it. Do not spoof senderUrl with the API URL. Change validation to separate trusted actual document identity from configured API identity. Main's live `ownsDocument(event)` is authoritative; allow precisely the application's custom-protocol document, not every opaque/null origin.
2. **Stale objects are not fresh authorization.** S2 snapshots caller-supplied sender/context objects before a dialog and compares them afterward; unchanged stale copies cannot prove the window still owns the document or the user is still signed in. Main must re-read actual event frame/webContents, URL, current token+user, server and generation after native confirmation and immediately before the write. Use a revalidation closure in the main adapter, not renderer booleans. Bind native dialog parent to the verified window; cancellation/window destruction/logout rejects with zero grant write. Call one native dialog inside broker setGrant's confirmation path; do not pre-confirm then confirm again.
3. **Auth generation currently means document generation.** `main.mjs:855` increments authGeneration on trusted reload; S2 persists that generation inside grant identity. Reusing this counter strands persisted consent after reload and can collide across process launches because it starts at zero. Introduce separate cryptographically random authenticated-session generation, saved with the existing safeStorage session metadata and restored only with the matching server/user/session. Rotate on fresh sign-in, token replacement, logout/server/user change; legacy stored auth without it gets a new generation and no previous-generation grants silently transferred. Document epoch still invalidates pending IPC on navigation but does not revoke the current authenticated-session consent. Main numeric user IDs must become validated String(user.id) for S2's string tuple. Generation is random metadata, never a token/key fingerprint. Current restoreAuthentication accepts encrypted stored shape without proving the session is still valid; sharing must remain unavailable until the normal authoritative session validation has established the restored identity, and invalidate on rejected/expired auth. Do not treat a renderer claim or mere stored-token presence as fresh authentication.
4. **No actual spawn receipt.** S3 only accepts backendEnv/context. `createSpawnRuntime:545-583` resolves env, spawns, probes HTTP+WS and returns an owned connection; S2 `recordSpawnResult` is not wired. Resolving env, viewing the tab, receiving renderer `ready`, or supervisor status cannot prove application. Add a main-only lifecycle callback to fork host options, associated with an opaque host/spawn-attempt identifier, default profile and the exact *accepted env variable names* (never values). Record successful application only after an actual owned child was spawned with those variables and accepted by the live host; readiness probes may provide a stronger ready state. Failure/timeout/disposal/exit must retire that attempt. Keep the frozen backendEnv request/result unchanged; associate attempts through the host-owned callback/closure rather than adding renderer authority fields.
5. **Attempt and exit state are missing in S2.** S2 has a single pending identity/generation and aggregate applied flag. A late env resolution after S3 timeout, failed attempt followed by retry, duplicate success, or ordinary child exit can otherwise leave false applied state. Extend internal bookkeeping with per-attempt correlation and an explicit stop/disposed observation. Reject stale/duplicate receipts; only accepted variable names can become applied. Clearing current application must not erase saved consent. Ensure timeout does not later arm a receipt that marks an uncredentialed child applied.
6. **Provider-level status is absent.** S1 reports source/provider readiness; S2 status exposes only any-grant configured/applied. A toggle cannot infer whether this particular provider is granted from the global flag. Add reference-only per-provider configured/effective lifecycle state bound to current identity, including accepted names/attempt state. Do not report all providers applied because one key was injected. Distinguish native Hermes-owned configuration from Rhythm static-key availability; OAuth source entries never enable grants.
7. **Conservative unreadable status matters.** S1 provider fallback can say absent while underlying Hermes `.env`/auth source is unreadable or malformed. S2 only explicitly excludes unknown auth version before injection. Main must not present that as proven absence or safe shadowing. Before granting application, unreadable/malformed native precedence information must fail closed (or a separately tested native provider precedence proof must justify injection). Preserve the source error in the value-free DTO.
8. **Disposal must be observable, not swallowed.** Current view disposeRecord catches host.dispose errors, and broker has no ordinary-disposal notification. On identity change, block new credential-bearing starts immediately, await all pending/active owned attempts and stop receipts, and keep sharing unavailable if disposal fails. Never claim revoked while an owned child can retain the old key. Existing fork dispose sets disposed and stops known connections; in-flight connect completes later and stops its owned child. The new lifecycle integration must await/account for that interval before accepting another identity. Do not await a broker serial queue callback that itself queues another broker operation: avoid a disposal/receipt deadlock.

## Concrete wiring flow

1. Main derives OS home from OS user information and validates canonical default Hermes home; no renderer path input and no ambient HOME override for production identity. Missing/unreadable home means unavailable until Hermes owns initialization; readiness does not create/write Hermes stores. Create only Rhythm's grant directory under userData, with 0700, and grant file 0600. Main getter yields authenticated session tuple or null; all statuses/mutations require owning main document plus authenticated user.
2. On status request, inspect S1 and current broker references only; return a closed bounded value-free DTO. Suggested shape: `{version:1, availability, sources, providers:{openrouter,...}, lifecycle, childMayRetainCredential, memory:{state:"disabled"}, claudeCode:{state,refreshGuarantee}}`. Each provider has separate `sourceState`, `nativeState`, `grantEnabled`, `applicationState`. No paths, session tokens, account keys, fingerprints, raw exceptions or raw file JSON.
3. On mutation request, accept only source `opencode-auth-json`, four enum providers and enable/disable. Broker's queued mutation invokes main confirmation once with fixed provider/action text, then fresh main revalidation. Success changes consent only; UI remains configured/pending until actual future start. Disable while a child is running says it may retain the key until stop. Do not force restart silently merely to change the status label.
4. When embedded host is created, main supplies frozen trusted backendEnvContext and explicit canonical hermesHome, plus callback closures checking current auth/host generation. Default-owned spawn alone can request keys. Each successful attempt emits the actual applied provider-name set. Borrowed/nondefault backend emits no key request and no applied receipt. Host disposal/exit clears active application; saved grants remain.
5. Logout/server/user/auth-generation change immediately rejects IPC and pending callbacks, disposes owned credential-bearing runtime(s), invalidates applied state, and only then permits next identity to create a host. Main's existing logout/server-change paths already call disposeCurrent; coordinate broker invalidation into those paths and app shutdown. Trusted reload invalidates document requests and clears stale UI responses; reattached view uses the same authenticated-session consent with a new runtime attempt.
6. In Accounts inspector, keep current OpenCode login/key entry flows untouched. New panel has provider status, explicit Share/Stop sharing actions and refresh/error text. Native dialog owns confirmation; web does not simulate it with window.confirm. Clear view state on identity change/unmount and ignore stale async replies. Non-Electron fixture/browser shows unavailable, not invented grants. Use inspector-side controls in shared ListInspector; no localStorage consent or authority.
