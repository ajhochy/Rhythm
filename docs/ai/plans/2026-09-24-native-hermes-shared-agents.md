# Shared Rhythm/Hermes agents, settings, memory, and delegation

Planning only, 2026-09-24. Source inspected: Rhythm `.mega-wt/integration` (`mega/2026-09-18-mobile-electron-hermes`, PR #1544) and Hermes fork `8ea642dbb6a8b8d65868c3e7a468c471914f037b`. No source, issue, live configuration, credential store, or server was changed. Only this file was written. This is an implementation proposal, not runtime evidence.

## Intent and constraints

Goal: AJ sees the same named Rhythm agents and their canonical settings from Rhythm and embedded Hermes, can actually run supported shared agents in either runtime, can delegate between runtimes in either direction, and can deliberately access shared long-term memory; all work stacks into mega PR #1544, with one combined smoke campaign after integration.

**Resolved user decision (follow-up): “No, Hermes should run it itself.”** Selecting a shared Rhythm agent in Hermes must execute the native Hermes AIAgent, with that agent's canonical settings and permissions applied. Launching OpenCode behind a Hermes UI, proxying its transcript, or calling an ordinary LLM completion does not satisfy this decision. Two-way delegation remains required. Unsupported semantics must be implemented for completion; a clear launch refusal is a temporary safety boundary and cannot be counted as completed parity.

Scope: shared named-agent catalog/editor, explicit runtime applicability, executable policy projection, an authenticated local cross-runtime delegation bridge, #1569 memory/credential slices, and integrated qualification. The native Hermes profile remains a credential/runtime identity; it is not renamed into or merged with a Rhythm agent. Shared agents are selections within that runtime identity.

Non-goals: sharing OAuth refresh tokens; merging native Hermes profile stores; overwriting `~/.hermes` files; exposing local agent APIs on the hosted production API; mirroring transcripts or databases; arbitrary API proxying; changing standalone Hermes profile isolation; automatic migration, installation, deployment, or merge. Preserve existing native Hermes agents/profiles/settings; distinguish their source from shared agents.

Hard constraints: main/backend-only authority; strict capability scope; user/server/profile/runtime generation binding; no renderer-supplied caller identity or arbitrary endpoints; immutable session policy snapshots; deny unsupported security semantics rather than silently flatten; only synthetic fixtures and sanctioned sandbox for testing. The integration AGENTS.md requires four fixture/path environment variables for `tools/dev/sandbox.sh`; no hand-started api_server. Existing dirty integration/fork artifacts belong to other work and must be preserved.

Tensions: one understandable agent identity versus different engine capability/policy models; same settings versus preserving host-specific options; convenient delegation versus parent/owner authorization; live edits versus Hermes frozen prompt caching. Solve these with one canonical shared definition, explicit engine projections, stable native identities, and new-session application of settings.

Cheapest vertical proof: create two synthetic shared agents (manager and specialist) with a prompt marker, explicitly supported model and restrictive portable permissions; open the same ID/revision in both UIs; launch one in each engine and observe the marker plus one denied operation; send one delegation in each direction and observe the result in the originating parent; search a unique synthetic vault note in Hermes without any write. A catalog-only or prompt-only implementation does not prove this goal.

## Clarification interview

Parent task explicitly directs bounded read-only planning and reasonable defaults without further user questions. The subsequent user clarification explicitly requires native Hermes execution. Remaining implementation defaults: canonical shared agents originate in Rhythm; both hosts edit that same definition; engine-specific settings remain explicit; default topology is the embedded local Hermes runtime already owned by Rhythm. An unsupported runtime configuration is visibly blocked and is not counted as completed parity. Standalone/remote Hermes remains unavailable unless separately connected through an authenticated approved host capability. ## Proposed contract

### Shared identity and settings

Keep `AgentConfig.id` as the canonical shared agent ID. Add a versioned host-neutral DTO with canonical revision, label, settings, and per-runtime readiness/applicability (`supported`, `unsupported`, `unavailable`, `pending-new-session` plus reasons). Use `(Rhythm server identity, signed-in user, shared agent ID)` for UI cache scope and stable linkage. Native Hermes `(connection, profile)` is a separate runtime destination. Names are presentation only.

Both host editors PATCH only changed canonical fields with an expected revision. A conflicting save returns conflict and retains the local draft. Preserve null/inherit versus explicit empty lists/false, JSON ordering where policy evaluation depends on it, unknown values, advanced patterns, security locks, account bindings and fields not understood by the editing host. Never deserialize into a smaller object and overwrite the whole profile. If the current controller lacks revision compare-and-swap, add it for the new shared-edit endpoint rather than pretend `revision` alone prevents lost updates.

Runtime projections are computed from the full canonical definition and actual runtime capabilities. Minimum portable semantics: identity, prompt, selected supported provider/model, supported reasoning, explicit tool/MCP/skill allowlists, availability/lock status, manager/delegate roster. Inheritance resolves to a concrete, auditable policy for the chosen runtime; it must not silently mean all Hermes tools. OpenCode plan/build mode, ordered permission patterns, account bindings, native image-generation permission, custom skill IDs, and unknown policy are **not** assumed portable. Preserve and display them. If a security-critical policy is unsupported, launch is blocked with the exact reason. Noncritical host-specific choices can remain visible and unapplied only with an explicit applicability label. No automatic weakening or clearing of restrictions.

A new shared-agent launch freezes canonical ID/revision and effective policy into the native session. Saving settings affects future sessions; existing Hermes prompts are not rewritten. On resume, restore the same snapshot. Immediate security lock or grant revocation prevents new protected actions/launches through the bridge without falsely claiming to remove already delivered context or secrets.

Do not create one native Hermes home per Rhythm agent or write `config.yaml`/SOUL as a sync mechanism. Extend a generic, optional session-policy provider seam only where existing plugin APIs cannot enforce the concrete launch projection. Rhythm mapping stays in `plugins/rhythm`; generic host code accepts validated policy/capability data, not Rhythm-specific branches. Existing plugin ownership contract must explicitly permit the narrow generic seam before implementation.

### Local bridge and two-way delegation

Use one local execution bridge with operation-specific capabilities, separate from the hosted workspace client. Reuse #1569's host-owned lifecycle/identity binding pattern, not its memory-read token for writes. Expose narrow operations such as catalog/read, profile patch, launch, delegation dispatch/status/result/cancel. Main establishes the capability with the owning local server and pinned Hermes backend. Tokens/endpoint selection remain main/backend-only. Absent capability means unavailable. No hosted token grants blanket local execution.

Keep a small durable local bridge job ledger with native session references `{runtime, runtimeInstance, sessionId}` for parent/child; never put fabricated Hermes IDs into `agent_sessions`, or read/write Hermes SQLite directly. Record shared target ID/revision, actor, generation, chain/depth, idempotency key, state, bounded result and delivery receipt. Use additive local schema; if the API also supports agent-execution Postgres deployments, provide the required bootstrap parity or explicitly keep this bridge local-only outside that DB surface.

Hermes -> Rhythm: plugin tool obtains its actual Hermes execution context; the bridge binds it to the main-established user/profile/generation. Resolve manager and delegate roster server-side, launch a real Rhythm target through existing profile-scoped runner mechanics, return opaque job ID, then deliver/poll the bounded result only to the same authenticated parent. Do not use AGENT_LOCAL caller-owner fallback with a supplied ID.

Rhythm -> Hermes: MCP obtains its actual SDK caller context; the bridge validates the existing manager and delegation rules, selects the owned Hermes destination, and requests a real native Hermes session with the target's validated frozen projection. Use `session.create`/prompt/status/interrupt via a narrow backend adapter; do not treat a generic LLM completion as an agent. Preserve native cancellation/approval behavior. Native Hermes subagent lifecycle may be reused when there is a real native parent, but must not be fed a synthetic parent agent.

Both directions: revalidate caller ownership, target lock/enabled state, exact target, policy revision, runtime generation, model readiness, cwd authority and chain depth before dispatch. Cap the shared chain at the existing depth 2, counting cross-runtime hops, so bounce-back cannot reset depth. Idempotent retry yields the same job, never a duplicate child. A native start with uncertain acknowledgement yields `unknown/needs-reconciliation`, never automatic resubmission. Cancellation only targets that job's owned child; completion/cancel races cannot overwrite an already terminal result. Runtime restart/disposal marks unconfirmed running jobs unknown/interrupted; native identity reconnection must prove continuity. Deliver completion once to the original parent; background return must not inject a fresh user message into an unrelated active chat. Errors and status omit transcript text unless requesting the authorized result operation.

## First independent implementation slice: N0 native frozen session policy

**Purpose:** establish the smallest trustworthy native Hermes execution primitive before UI, credential broker, catalog, or cross-runtime job wiring. This is the first implementation slice for the new agent-parity work; #1569 S5 can independently proceed in parallel. Native execution is mandatory at completion even though N0 starts with a bounded policy subset.

**Scope:** a generic session-policy provider registered through the plugin facade, and a frozen resolved session-policy snapshot passed through real native session create/build/resume.
